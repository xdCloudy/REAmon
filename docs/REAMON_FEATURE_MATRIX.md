# REAmon feature matrix

This matrix describes product capabilities, not a promise that every engine or input
works for every artifact. “Implemented” means a workflow exists in the current
checkout; it does not imply broad fixture coverage or behavioral equivalence. See the
[language matrix](REAMON_LANGUAGE_MATRIX.md) for format-level limits.

The full artifact-to-export sequence, with evidence gaps for each stage, is in the
[reconstruction stage matrix](REAMON_RECONSTRUCTION_STAGES.md).
Dedicated P1 acceptance gates for type recovery, behavioral validation, static/dynamic
fusion, whole-project rebuilding, and provider reconciliation are in the
[agentic reconstruction milestone specification](REAMON_RECONSTRUCTION_MILESTONES.md).
Protected-binary stages and benchmark gates are specified in the
[protected-binary recovery milestone](REAMON_PROTECTED_BINARY_RECOVERY.md).

## Optional IDA Pro analysis

IDA Pro is supported as a bring-your-own licensed native provider. The batch `idat`/`idat64` process runs inside the REAmon Linux runtime from a read-only `/opt/ida` mount, with its executable path stored in Settings. Results retain Hex-Rays pseudocode, disassembly, addresses, call edges, and exact input hashes. It needs no IDA API key. A Windows client install is not visible to the server; a paired native runner remains future work. See the [IDA Pro integration guide](REAMON_IDA_PRO.md).

## Paginated MCP relationships

Inspired by [ReVa's Ghidra cross-reference tools](https://github.com/cyberkaida/reverse-engineering-assistant), `workspace_list_code_relationships` pages through stored call edges or field/string references for one code unit. Every result is restricted to the active import and the selected unit's exact artifact, provider, and analysis task. This complements the bounded relationship preview in `workspace_get_code_unit`; it does not infer missing edges or claim that persisted references prove behavior.

## Native deobfuscation follow-up

REAmon uses the MIT-licensed [Ghidra Deobfuscation Lab](https://github.com/xubin0903/ghidra-deobfuscation-lab) `CffCore` for read-only, confidence-labeled control-flow-flattening evidence and offers `BcfClean` and `CffDeflatten` as separate opt-in Ghidra passes. Each scan is capped at 32 function candidates, uses upstream's per-function emulation checks and mismatch reversion, and stores its own patch log and hash-checked cleaner pseudocode as a separate visualizer alternative. Exact-address output enters AI rewrite context only after the provider version, artifact hash, saved source, and successful audit all match. The imported binary and baseline decompilation are preserved. Both passes remain experimental pending REAmon fixture comparison; they target known OLLVM bogus predicates and CFF patterns rather than arbitrary obfuscation. See the [upstream reuse audit](REAMON_UPSTREAM_REUSE.md#additional-engines-evaluated).

## AI attempt evidence snapshots

The rewrite attempt history summarizes the saved context for each file or function attempt with a SHA-256 evidence-context fingerprint, the project-memory categories used, and up to 16 related unit names and languages. The summary reads the request payload persisted with the database attempt; it does not return related source snippets. Batch members show their own context so reviewers can compare the evidence used across parallel function work.

## Product-critical distinctions

- Decompilation output and AI-maintained source are separate artifacts.
- A completed provider task is not proof of full analysis coverage.
- A parsed candidate is not necessarily compilable; a compiled candidate is not
  necessarily behaviorally equivalent.
- A recovered name is a proposal until its evidence and review state are recorded.
- Similarity helps locate useful examples, but project identity and behavioral claims
  require stronger evidence.

For the intended process and state model, see [the workflow](REAMON_WORKFLOW.md).
