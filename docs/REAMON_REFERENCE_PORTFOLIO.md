# REAmon reference portfolio

This portfolio records external projects that can speed up REAmon. Each reference
has a specific job: reuse an engine through an adapter, learn a workflow, or compare
outputs. It does not mean REAmon has integrated or validated that project. Before
shipping copied code or binaries, confirm the exact version, component license,
dependencies, and notices.

The detailed source audit, current integration notes, and license constraints are in
[upstream reuse](REAMON_UPSTREAM_REUSE.md). The portfolio below is the short list for
product and engineering planning.

## Priority references

| **P0 workflow: [decomp.wtf](https://github.com/i12bp8/decomp.wtf)** | Bounded function claims, assembly and neighbor context, saved attempts, target-compiler feedback, match promotion, and regression protection. | It demonstrates a disciplined path from machine code to maintainable source, with evidence and measurable acceptance. | Make each function/method/class a persisted work unit; provide scoped evidence and project memory; retain every attempt; validate with the strongest available language-specific method; promote reviewed results without overwriting provider output. | Archived project specialized for reproducibly rebuilt targets. Adapt its workflow, not its game-specific compiler, SQLite store, or whole application. Highest workflow priority. |
| **P0 coordination: [decomp-agents](https://github.com/swstegall/decomp-agents)** | Isolated worktrees, atomic per-function claims, bounded workers, audit logs, and human escalation for merge conflicts. | It shows how parallel work can avoid duplicate or conflicting changes when the target has a reliable grader. | Later, add leases over REAmon unit IDs, attempt caps, conflict-aware source promotion, resumable workers, and auditable merge/escalation records. | Coupled to meteor-decomp, Claude SDK, and a specific legacy toolchain. | **P0 safe source edits: [Humanify](https://github.com/jehna/humanify)** | Current v3 is a Rust CLI using OXC to apply JavaScript identifier renames across lexical scopes, with reserved-word and collision handling. OXC's current Node binding does not expose its semantic scoping model, so REAmon's prototype uses Babel's scope-aware API while evaluating a Rust/OXC adapter. JavaScript-only scope safety is not a universal transformer or behavior proof. |

Persist artifact hash, provider revision, detected compiler version, recovered Rust constructs, warnings, output bytes, and runtime. Use compilation/execution only in a separate fixture harness with known source; never treat successful pseudocode generation as behavioral validation. | BSD-2-Clause angr project. Output is pseudocode, not guaranteed compilable or original Rust. The upstream evaluation project reports comparison metrics for conciseness, fidelity, and type recovery over real-world Rust programs; REAmon fixture results remain pending. |
| **P1 native evidence comparison: [RetDec](https://github.com/avast/retdec)** | Retargetable LLVM-based native decompiler. ## Adoption order

1. Continue the decomp.wtf-inspired lifecycle in REAmon's project database. Attempt
   history, exact-source rewrite leases, durable queued rewrite requests, run-token
   worker claims, explicit review receipts, and source-hash compare-and-swap promotion
   guards are implemented. Queued work survives restarts; active jobs renew source
   leases and can be cancelled; a claimed attempt interrupted by worker loss is
   recorded and can be retried. Completed results can be restored into the editor,
   with exact-input matching before member-level merging. MCP now exposes saved code
   units and bounded function dossiers from project memory so agents can inspect the
   exact function, provider, artifact, and same-task call edges before editing. Next
   add language-specific validators and validation regression protection.
2. Build the provider fixture and validator contract. Use decomp.me/objdiff as a
   reference for exact-build feedback, but isolate any target compiler/build process.
   Include a language-specific parser/build check and persist what each check proves.
3. Add syntax-aware safe edits. Compare Humanify and ast-grep patterns, make all edits
   source-hash-bound and reviewable, then validate with the matching language toolchain.
4. Use Joern's CPG as a schema and query-pattern reference for cross-language evidence;
   keep REAmon's relational observation store authoritative and graph projection
   reproducible.
5. Compare alternate language/native engines where a measured gap exists, then add
   targeted symbolic or dynamic analysis only when a concrete investigation question
   needs it.
6. ToCode export indexing now has an early workspace-import slice: bounded function
   metadata, copied decompiled source, same-export calls, and explicit folder mapping
   call edges are stored in REAmon's task/observation database and visualizer. Complete
   hash-backed input-to-export provenance, more APK/.NET metadata, and representative
   fixture validation before calling the adapter broadly supported. Never make ToCode's
   export tree or generated agent files a second database of record.

Do not prioritize a reference because it is popular alone. A proposed reuse should
close a named language, workflow, validation, or usability gap and pass a fixture-based
comparison. Track decisions and revisions in the [upstream reuse audit](REAMON_UPSTREAM_REUSE.md).

## Current status of decomp.wtf

The upstream repository was archived on 2026-10-15. Its maintainer says development
and releases have stopped, while the code remains available under MIT. The maintainer
also records community opposition to AI-assisted decompilation as the reason for
stopping. REAmon uses the repository as a fixed, inspectable workflow reference; it
must not imply endorsement by the decompilation communities or submit AI-generated
work to another project without that project's rules and explicit review. Read the
[upstream notice](https://github.com/i12bp8/decomp.wtf) before using any snapshot.
