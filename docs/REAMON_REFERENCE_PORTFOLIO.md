# REAmon reference portfolio

This portfolio records external projects that can speed up REAmon. Each reference
has a specific job: reuse an engine through an adapter, learn a workflow, or compare
outputs. It does not mean REAmon has integrated or validated that project. Before
shipping copied code or binaries, confirm the exact version, component license,
dependencies, and notices.

The detailed source audit, current integration notes, and license constraints are in
[upstream reuse](REAMON_UPSTREAM_REUSE.md). The portfolio below is the short list for
product and engineering planning.

## Priority references

| Priority and reference | What it contributes | Why REAmon references it | What REAmon should adapt | Limits and status |
| --- | --- | --- | --- | --- |
| **P0 workflow: [decomp.wtf](https://github.com/i12bp8/decomp.wtf)** | Bounded function claims, assembly and neighbor context, saved attempts, target-compiler feedback, match promotion, and regression protection. | It demonstrates a disciplined path from machine code to maintainable source, with evidence and measurable acceptance. | Make each function/method/class a persisted work unit; provide scoped evidence and project memory; retain every attempt; validate with the strongest available language-specific method; promote reviewed results without overwriting provider output. | Archived project specialized for reproducibly rebuilt targets. Adapt its workflow, not its game-specific compiler, SQLite store, or whole application. Highest workflow priority. |
| **P0 coordination: [decomp-agents](https://github.com/swstegall/decomp-agents)** | Isolated worktrees, atomic per-function claims, bounded workers, audit logs, and human escalation for merge conflicts. | It shows how parallel work can avoid duplicate or conflicting changes when the target has a reliable grader. | Later, add leases over REAmon unit IDs, attempt caps, conflict-aware source promotion, resumable workers, and auditable merge/escalation records. | Coupled to meteor-decomp, Claude SDK, and a specific legacy toolchain. Reuse coordination ideas only after REAmon's unit lifecycle and validator contracts are stable. |
| **P0 safe source edits: [Humanify](https://github.com/jehna/humanify)** | LLM-suggested JavaScript identifier names applied through scope-aware AST transforms. | It separates uncertain AI suggestions from deterministic source edits, reducing accidental syntax and reference damage. | Have models propose symbol mappings with evidence and confidence; apply accepted renames through language-aware AST/refactor APIs; retain diffs and undo history. Extend the pattern across language providers. | JavaScript-focused and identifier-renaming-focused. Its output is not semantic proof and should not be copied as a universal source transformer. |
| **P0 universal parsing: [Tree-sitter](https://github.com/tree-sitter/tree-sitter)** | Error-tolerant syntax trees and a broad set of language grammars. | Shared syntax tooling can support navigation, unit boundaries, safe edit scopes, and syntax checks across many source languages. | Use syntax trees to identify declarations and validate structure; add language-specific symbol resolution and compiler checks where available. | Grammar availability is not decompiler support. Parser and grammar licenses/notices vary; a parseable tree does not establish behavior or idiomatic recovery. |
| **P0 source refactoring: [ast-grep](https://github.com/ast-grep/ast-grep)** | Tree-sitter-backed structural search and rewrite rules, with diffs and interactive application. | It offers a practical AST-aware mechanism for controlled code edits across many grammars. | Prototype as an optional edit backend for deterministic pattern-based transformations; keep AI rename proposals separate, show a diff, apply only to exact source-hash/version ranges, then parse and run the language validator. | Pattern rewrites are not symbol-resolution-aware refactors by default. Evaluate custom language/parser trust, grammar licensing, and scope correctness before broad project-wide renames. |
| **P1 exact-build judging: [decomp.me](https://github.com/decompme/decomp.me) + [objdiff](https://github.com/encounter/objdiff)** | decomp.me provides collaborative, compiler-configured function matching; objdiff compares rebuilt object files, function/data units, and progress. | They make compilation feedback actionable and show how a correct visualizer can explain mismatches instead of reporting a single opaque score. | Define a validator contract for a user-supplied build recipe, expected object/function, compiler identity, normalized instruction diff, and reproducible outcome. Consider objdiff's local/WASM comparison model for native exact-build slices. | Their strongest validation is for configured compiler/toolchain targets, not arbitrary binaries or source equivalence. Never run untrusted build scripts in the web process; use isolated execution, resource/time caps, and explicit opt-in. decomp.me and objdiff licenses are permissive, but check component dependencies. |
| **P1 Python comparison: [PyLingual](https://github.com/syssec-utd/pylingual)** | A CPython bytecode decompiler with cross-version reconstruction techniques and a local CLI. | Compare reconstruction quality with the currently integrated pycdc path on a versioned, reproducible fixture set. | Build a provider comparison harness; record Python bytecode version, structural recovery, parse/compile results, warnings, and resource use; make alternate provider output reviewable. | GPL-3.0 and model/runtime requirements need distribution review. Upstream notes local control-flow accuracy may differ from its hosted service. Candidate for comparison, not a default replacement. |
| **P1 Rust recovery: [Oxidizer](https://github.com/sefcom/oxidizer), now in angr** | Rust-aware native decompilation techniques for compiler/runtime cleanup, Rust type inference, enum/`Result`/`Option` recovery, macro outlining, and structured Rust pseudocode. The original project says Oxidizer has merged into angr. | Rust is a major language where generic C-like pseudocode loses Rust-specific compiler patterns and idioms; this is a specific upstream-backed route to measure the gap. | Prototype the angr Rust analysis as an optional isolated provider. Compare against Ghidra on pinned Rust fixtures spanning compiler versions, stripped/debug builds, and architectures; persist source hash, toolchain identity, recovered constructs, diagnostics, and runtime. | BSD-2-Clause angr project. Output is pseudocode, not guaranteed compilable or original Rust. Pin angr and its native dependencies; confirm the analysis API and license notices at the selected commit before integrating. |
| **P1 Lua dialect comparison: [unluac-rs](https://github.com/x3zvawq/unluac-rs)** | A Rust library/CLI and browser workspace claiming Lua 5.1–5.5, LuaJIT 2.1, and Luau bytecode dialects, with control-flow and binding-aware reconstruction. | It may cover more Lua dialects than REAmon's separate standard Lua and LuaJIT providers and offers a practical comparison target. | Compare its CLI/library with existing providers using versioned fixtures; record exact dialect detection, source parse/runtime outcome, malformed-input behavior, and resource bounds before selecting any provider. | MIT-licensed upstream; the broad version claims still require independent validation. Keep LuaJIT, Luau, and standard Lua results distinctly labeled and retain existing provider output. |
| **P1 WebAssembly bridge: [WABT `wasm2c`](https://github.com/WebAssembly/wabt/tree/main/wasm2c)** | Converts a WebAssembly module into equivalent C source and a header, plus a runtime interface. | It can give the current WAT-level view a useful higher-level, compilable representation for analysis and navigation. | Offer generated C as a clearly labeled semantic bridge; preserve the original Wasm, names, module structure, and runtime dependency; test equivalence against the Wasm engine. | Generated C represents Wasm semantics and runtime mechanics, not the original C/C++/Rust/AssemblyScript source. REAmon currently uses WABT for low-level WAT/function navigation. |
| **P1 native comparison: [rev.ng](https://github.com/revng/revng) and [Reko](https://github.com/uxmal/reko)** | Alternative native decompilation approaches, architecture coverage, structured models, and C-like output. | Independent engines can expose Ghidra blind spots and help compare function boundaries and source quality across native fixtures. | Prototype isolated, optional adapters for selected architectures; compare normalized output, function coverage, type recovery, buildability, runtime, and provenance against Ghidra. | Both have GPL-family distribution considerations and substantial toolchain/runtime footprints. Evaluate exact components and licenses before bundling; avoid redundant default analysis. |
| **P1 native analysis: [angr](https://github.com/angr/angr)** | Binary loading, CFG recovery, symbolic execution, and data-dependency analysis across architectures. | It can answer focused path, branch, and data-flow questions that a decompiler listing alone cannot resolve. | Add opt-in, question-bounded analyses; store entry state, constraints, timeout, explored paths, and result provenance as evidence connected to code units. | BSD-2-Clause project license, but broad dependencies and path explosion make this a targeted optional provider rather than a default pass. It produces analysis evidence, not maintainable source. |
| **P1 language-neutral code graph: [Joern](https://github.com/joernio/joern)** | Code Property Graph model and query engine spanning source, bytecode, and selected binary inputs. | Its graph model is a useful design reference for connecting syntax, control flow, data flow, and calls across provider outputs. | Compare its node/edge semantics with REAmon's persisted observations and Neo4j projection; adapt useful typed relationships and query patterns through an adapter, not a second source of truth. | Joern is a substantial Scala/JVM stack with a custom graph database and a security-analysis focus. Confirm exact license/dependency terms and format fidelity before deploying it; its listed language support is not a guarantee of source recovery. |
| **P1 language-specific engines: [JADX](https://github.com/skylot/jadx), [ILSpy](https://github.com/icsharpcode/ILSpy), [webcrack](https://github.com/j4k0xb/webcrack), [pycdc](https://github.com/ejfkdev/pycdc), [unluac](https://github.com/Jeong-Min-Cho/unluac), and [LuaJIT Decompiler](https://github.com/marsinator358/luajit-decompiler-v2)** | Mature format-specific decompilers, deobfuscators, and source reconstruction. | Language-specific tools generally recover more useful structure than one generic native pseudocode engine. | Keep REAmon's existing isolated providers; record source hash, engine/version, warnings, output lineage, and validator evidence; compare alternate providers on fixtures before promoting support. | These are distinct input families and maturity levels, not one shared guarantee. Current integration and caveats are recorded in the [language matrix](REAMON_LANGUAGE_MATRIX.md). |
| **P2 broad recovery survey: [Disrobe](https://github.com/1-3-7/disrobe)** | Broad static decompiler/deobfuscator/unpacker coverage and an MCP investigation surface. | Its catalog is useful for discovering long-tail formats, obfuscators, and investigation operations that REAmon's provider matrix may not yet enumerate. | Use its public catalog and format taxonomy as a gap-discovery checklist; independently locate permissively licensed upstream engines for any promising format. | The current Disrobe license is source-available/proprietary and requires a paid license for company use. Do not copy, bundle, or depend on its source/binary for REAmon; its feature claims require independent validation. |
| **P2 runtime evidence: [Frida](https://github.com/frida/frida-core) and [Qiling](https://github.com/qilingframework/qiling)** | Instrumentation or emulation for observing behavior in a controlled runtime. | Dynamic traces can answer questions static output cannot, such as runtime-selected paths, resolved calls, or data transformations. | Add opt-in session adapters that attach traces to exact artifact hashes, environment details, and reproducible test inputs; link observations back to functions and hypotheses. | Runtime behavior is sample- and environment-dependent. These tools provide evidence, not source recovery; isolation and component licenses need review. |

## Adoption order

1. Finish the decomp.wtf-inspired lifecycle in REAmon's project database: atomic
   unit claims, bounded evidence context, attempt history, validator outcomes,
   explicit review receipts, and guarded promotion. Attempt history and exact-source
   rewrite leases are implemented; worker ownership, review receipts, validator breadth,
   and promotion guards remain open.
2. Build the provider fixture and validator contract. Use decomp.me/objdiff as a
   reference for exact-build feedback, but isolate any target compiler/build process.
   Include a language-specific parser/build check and persist what each check proves.
3. Add syntax-aware safe edits. Compare Humanify and ast-grep patterns, make all edits
   source-hash-bound and reviewable, then validate with the matching language toolchain.
4. Use Joern's CPG as a schema and query-pattern reference for cross-language evidence;
   keep REAmon's relational observation store authoritative and graph projection
   reproducible.
5. Compare alternate language/native engines where a measured gap exists, then add
   targeted symbolic or dynamic analysis only when a concrete investigation question
   needs it.

Do not prioritize a reference because it is popular alone. A proposed reuse should
close a named language, workflow, validation, or usability gap and pass a fixture-based
comparison. Track decisions and revisions in the [upstream reuse audit](REAMON_UPSTREAM_REUSE.md).

## Current status of decomp.wtf

The upstream repository was archived on 2026-10-15. Its maintainer says development
and releases have stopped, while the code remains available under MIT. The maintainer
also records community opposition to AI-assisted decompilation as the reason for
stopping. REAmon uses the repository as a fixed, inspectable workflow reference; it
must not imply endorsement by the decompilation communities or submit AI-generated
work to another project without that project's rules and explicit review. Read the
[upstream notice](https://github.com/i12bp8/decomp.wtf) before using any snapshot.
