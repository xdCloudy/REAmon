# REAmon reconstruction stage matrix

REAmon's target is a traceable path from imported artifact to reviewed, validated,
maintainable export. Stages may run in different orders or be unavailable for a given
format. A completed task means its provider finished; it does not mean every unit
passed through every stage.

| Stage | Current status | Evidence and current limit | Completion evidence to add |
| --- | --- | --- | --- |
| Artifact ingestion | Integrated | File and folder imports preserve artifact identity, hashes, and provenance. Browser uploads use resumable chunks or bounded streaming; storage capacity remains the practical limit. | Exercise recovery after interrupted large imports on a clean deployment and verify all bytes against the saved hash. |
| Analysis | Integrated, provider-dependent | Providers discover and profile units; saved coverage distinguishes discovered, returned, observed, indexed, omitted, and unvisited units where the engine reports them. | Extend explicit coverage reporting across providers and validate large, mixed-format projects. |
| Static and dynamic analysis fusion | Planned integration | Static providers persist artifact/run/function/control-flow evidence; runtime analysis is not yet mapped generally to stable static identities with ASLR-aware provenance. | Correlate authorized runtime events with modules, relocation maps, functions/blocks, input conditions, coverage, and uncertainty; meet M3 overhead and mapping gates while retaining static-only operation. |
| Disassembly | Integrated for several formats | Ghidra, JADX, and format-specific providers store instructions or equivalent low-level evidence. | Compare address and instruction coverage against versioned fixtures across architectures and formats. |
| Decompilation | Integrated, uneven language coverage | Multiple providers emit source-like output for Android/Java, .NET, Python, WebAssembly, and native targets. Output fidelity and coverage vary; native C-like pseudocode is not recovered original source. | Measure unit coverage and source fidelity per toolchain, version, optimization level, and obfuscation class. |
| Multi-provider semantic reconciliation | Partial comparison with bounded failed-run unit fan-out | Hash-linked alternatives, bounded diffs, instruction similarity, analyst-reviewed cross-provider function matches, and persisted failed/cancelled run cases exist. The visualizer presents up to 32 hash-verified compatible provider outputs beside the selected result and marks when its bounded 500-task/500-observation history omits evidence. An operator can queue one or up to five captured instruction-evidence units per case to the durable reconstruction worker for 12 source languages when a syntax grammar is available; each unit has its own stable attempt identity and persisted draft/lifecycle. Behavior remains unvalidated. Semantic disagreements are not generally adjudicated. | Add resumable case budgets and targeted provider re-analysis; extend provider-complete retrieval beyond current UI bounds; detect material boundary/CFG/type/reference/logic disagreements; preserve hypotheses and original outputs; and meet M5 accuracy, calibration, and independent-provider gates. |
| Protected-binary identification and recovery | Early, bounded static PE and ELF evidence | PE inspection records sections, entry-point mapping, import/certificate directory locations, capped entropy samples, malformed raw ranges, suspected UPX markers, and capped DLL/import-name/ordinal evidence. Synthetic PE32 and PE32+ fixtures cover import names and ordinal values; import clues are persisted and shown in the project overview as static evidence, not behavior claims. Unavailable and truncated parsing states are visible in the overview. ELF inspection uses bounded `readelf` header/program/section output and records suspected UPX names, entry-point mapping anomalies, and writable/executable LOAD segments. These are hypotheses; there is no real-sample accuracy, extractor, commercial-protector support, layer graph, or dynamic observation. | Meet exact-version detection/false-positive gates, validate import parsing on broader real-format fixtures, preserve immutable hash-linked layers, report per-region coverage/unknowns, validate safe recovery, and connect blocked units to the resumable M5 agent queue. See [protected-binary milestone](REAMON_PROTECTED_BINARY_RECOVERY.md). |
| Encrypted-region identification and recovery | Planned | No calibrated classifier, executable-region mapping, or authorized plaintext capture is implemented. Entropy or a protector signature alone is insufficient evidence. | Meet M7 condition-classification, coverage, hash/address mapping, authorization, isolation, capture-integrity, interruption, cleanup, and validation gates. See [encrypted-binary recovery](REAMON_ENCRYPTED_BINARY_RECOVERY.md). |
| Virtualized-code reconstruction | Planned; provider-specific IR foundations only | No validated classifier separates VM dispatch/runtime from protected application logic; no general custom-opcode semantics or equivalent-source workflow exists. | Meet M8 region/handler/semantic accuracy, mapping, replay consistency, budget, uncertainty, and behavior-oracle gates. See [virtualized-code recovery](REAMON_VIRTUALIZED_CODE_RECOVERY.md). |
| IR lifting | Early and experimental | Miasm simplified IR, Recurse function-scoped lifts, Ghidra p-code, and editable `.ud` views provide distinct intermediate evidence. These are not interchangeable and do not alone establish source semantics. | Report instruction and block coverage, unsupported operations, architecture/ABI, mappings, and fixture-backed behavior for each lifter. |
| Deobfuscation | Narrow experimental passes | Static or read-only passes target known patterns, including selected .NET cleanup and native control-flow transformations. Original artifacts and baseline outputs remain available. | Validate each pass against versioned obfuscated fixtures and confirm changes with a suitable compiler, differential check, or behavior test. |
| Type and symbol recovery | Partial | Providers and project memory retain names, types, references, relationships, and reviewed aliases with provenance and confidence. Recovery differs widely by format and stripped/debug state. | Measure symbol/type precision and recall against ground-truth fixtures; maintain stable project-wide identities. |
| Agentic Semantic Type and Data Structure Recovery | Partial, provider-specific | Ghidra, Go, DEX, ToCode, and Swift/Objective-C sources expose different type/prototype/layout metadata; no shared interprocedural reconciliation is validated. | Meet M1 signature, ABI/layout, type consistency, false-positive, provenance, and rollback gates by declared language/provider scope. |
| Agentic Semantic Symbol Recovery | Foundations partial; project-wide autonomy planned | Project memory, symbol snapshots, cross-provider matching, AI rename proposals, review receipts, and selected same-source binding-aware rename adapters exist. Autonomous whole-project naming, general cross-file propagation, and policy-driven acceptance are not implemented. Human review remains required. | Complete the separate ASSR-1/2/3 gates: project-wide discovery and semantic naming; language-aware cross-file binding/reference integrity; calibrated policy acceptance with deferral, immutable evidence, and exact rollback. Use compiled open-source ground-truth projects across stripped, obfuscated, optimization, language, and provider strata. See the [milestone specification](REAMON_SEMANTIC_SYMBOL_RECOVERY.md). |
| Source reconstruction | Early, reviewable workflow | AI drafts use bounded project database evidence; drafts, attempts, hashes, diffs, and review receipts are persisted separately from provider output. | Demonstrate consistent naming and structure across representative whole projects and reject unsupported claims through evidence-aware review; meet the distinct semantic-symbol recovery gates before claiming autonomous project-wide renaming. |
| Whole-project source assembly | Partial foundations | C#/Go accepted-source builds, single-class JAR replacement, APK rebuild, and provenance-rich source export are bounded workflows, not reconstruction of a complete application source tree. | Recover and classify files, modules, resources, dependencies, manifests, and entry points; retain stable links to binary evidence and explicit missing-information reports under M4. |
| Transpilation | Limited bridges | An early C#-to-Visual-Basic bridge follows ILSpy reconstruction and passes small cross-file compile/runtime fixtures. WebAssembly also has a generated Rust-shaped view; it is a bridge representation. Neither recovers the original source language. | Test obfuscated and project-scale bridges, report mappings and omissions, and add bridges only with versioned compile and behavior fixtures. |
| Compilation | Early, format-specific | One accepted Java class can be rebuilt into a derived JAR; the VB bridge has small fixture checks; `.ud` views have compile-back checks. | Add project-level builds, dependency and target-version handling, reproducible recipes, and broader fixture coverage. |
| Whole-project rebuilding and incremental repair | Partial, format-specific builds | C# and offline Go compile bounded accepted source sets; Java rebuild replaces one class in a JAR. General build recipes, dependency closure, and incremental project receipts remain open. | Achieve M4 supported-scope project build, dependency, reproducibility, cross-file, resource, and maintainability gates. |
| Validation | Partial, language-aware | Syntax validators cover multiple languages; a small set of translation and binary-view fixtures also checks compilation, runtime behavior, or byte identity. Syntax success is not behavior equivalence. | Tie every result to exact input/output hashes and expand compiler, differential, runtime, and malformed-input tests. |
| Autonomous behavioral and differential validation | Narrow fixture evidence; autonomous project-wide validation planned | Selected Lua and C#→VB fixtures compare runtime outputs; routine source receipts mostly validate structure or compilation and do not establish behavior. | Meet M2 oracle, branch coverage, discrepancy, replay, resource-bound, and worker-safety gates. Return unavailable if no safe executable oracle exists. |
| Iterative refinement | Integrated, still maturing | Function/file attempts, bounded parallel rewrites, cancellation, review, and saved project context support repeated improvement. The deployed visualizer can queue up to 10 functions across up to 40 source-linked units in a completed run, then link each saved result to its file for separate review. Browser and live-database acceptance remain pending. | Validate cross-file queue recovery and cancellation on a representative project; add reliable per-language quality measures and a fixture-backed loop that can explain and reproduce each improvement. |
| Export | Integrated, incomplete coverage | Reproducible bundles separate provider output and maintained source and include manifests, hashes, lineage, and accepted-review checks. | Validate imports in target tools and add complete rebuild/validation recipes and mappings for supported providers. |

The P1 type, behavior, static/dynamic fusion, whole-project rebuild, provider-reconciliation, encrypted-region, and virtualized-code gates are specified in [agentic reconstruction milestones](REAMON_RECONSTRUCTION_MILESTONES.md). Protection triage has its own [milestone](REAMON_PROTECTED_BINARY_RECOVERY.md). Existing semantic symbol recovery remains governed by the separate [ASSR specification](REAMON_SEMANTIC_SYMBOL_RECOVERY.md).

## How to use this matrix

Use the [language and format matrix](REAMON_LANGUAGE_MATRIX.md) for per-format
capability, the [feature matrix](REAMON_FEATURE_MATRIX.md) for product controls, and
the [readiness matrix](REAMON_READINESS_MATRIX.md) for release gates. The weighted
[progress matrix](REAMON_PROGRESS.md) estimates overall workstream completion; it does
not average these stages or certify a release.
