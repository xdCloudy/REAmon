# REAmon upstream reuse notes

REAmon should reuse mature reverse-engineering engines and adapt their evidence,
validation, and collaboration workflows to its project database. Engine output,
AI drafts, accepted maintained source, and validation results must remain
separate so a plausible name is never treated as proof of behavior.

## Current direction

### Large artifact transfer

The [tus resumable upload protocol](https://tus.io/protocols/resumable-upload.html)
uses a server-reported byte offset to continue an interrupted upload. REAmon's
project-scoped chunk endpoint already persists bounded chunks and returns the
confirmed file offset; the browser uploader now uses that response to skip any
prefix persisted by a previous attempt and reports progress from acknowledged
file positions. This is an adaptation of the protocol's offset-resume pattern;
REAmon does not implement the complete tus protocol or depend on `tus-js-client`.
The upstream JS client is MIT-licensed and remains a reference for retry and
browser persistence behavior, not copied code.

### Unity IL2CPP: distinguish metadata recovery from source recovery

An updated audit on 2026-10-19 compared the two viable MIT projects:

- [Cpp2IL](https://github.com/SamboyCoding/Cpp2IL) remains the candidate for
  method-body reconstruction. The last manual milestone is
  `2022.1.0-pre-release.21` at `12c8b4413900558a14e30adc4fc4d13d82383901`;
  current `development` is `b5ad444b82267cb1e4b88b8b373c008105bdea52` and targets
  .NET 10. Its README accepts a single APK and exposes `dll_il_recovery` through
  `--output-as`, but labels the tool WIP and says output can be rough. The
  development branch is rewriting its analysis around ISIL and CFGs. GitHub
  issue [#505](https://github.com/SamboyCoding/Cpp2IL/issues/505) reports Unity 6
  recovery output containing `throw null`; treat stub-body detection and exact
  method/address mapping as mandatory gates before indexing output as recovered
  source. This integration is still planned.
- [Il2CppDumper](https://github.com/Perfare/Il2CppDumper) can provide metadata
  and address maps that help label native functions. `master` is
  `4741d46ba9cd6159c5d853eb9d6fc48b4bfa2b1a`; release `v6.7.46` is
  `8a521b9c180cf13499253f0818cbc729dca767cb`. Its README says its dummy DLLs
  restore metadata **except code**, and lists Unity 5.3–2022.2. Open issue and
  PR activity requests Unity 6 metadata v39. Use it only as optional metadata
  evidence, never as a method-body decompiler or as a reason to claim C# source
  recovery. Preserve exact APK member paths and hashes for the native binary
  and `global-metadata.dat`. Its `script.json` schema includes `ScriptMethod`
  records (`Address`, `Name`, `Signature`, `TypeSignature`) and
  `ScriptMetadataMethod` records (`Address`, `Name`, `MethodAddress`), which
  gives a concrete route to address-scoped name evidence for matching Ghidra
  functions. Treat these as provisional metadata: integrate only after checking
  the exact binary/member hashes and address convention, and keep strings and
  metadata usage slots separate from method entry points. Upstream issue
  [#594](https://github.com/Perfare/Il2CppDumper/issues/594) documents incorrect
  string-literal addresses in an older release, so string references need their
  own fixture checks. REAmon now builds this pinned revision in an isolated
  analyzer image and stores bounded method metadata observations with the APK,
  metadata-member, and native-library hashes. RVA-to-Ghidra joins remain
  disabled until the address convention is verified on representative fixtures;
  this adapter does not recover method bodies or emit source.
- [Il2CppInspector](https://github.com/djkaty/Il2CppInspector) is suspended,
  AGPL-3.0, and explicitly not a decompiler. Keep it as a format and workflow
  reference; do not bundle or copy it into REAmon.

### PyInstaller executable extraction candidate

The MIT-licensed [pyinstxtractor-go](https://github.com/pyinstxtractor/pyinstxtractor-go)
snapshot audited at [`2aa0ec9`](https://github.com/pyinstxtractor/pyinstxtractor-go/tree/2aa0ec9e58317ac717fdeec84a02d5a67de7b96c2)
is a possible extraction stage before REAmon's existing pycdc provider. It extracts
Python modules from PyInstaller CArchive/PYZ bundles and reports the embedded
Python version. Its README says Python 2 PYZ archives and encrypted PYZ archives
are unsupported.

REAmon now vendors the audited snapshot's required Go files and MIT notice in
`analyzers/pyinstaller/upstream/`, pinned to the revision above. The adapter caps
input size, CArchive entries and compressed bytes, expanded data, PYZ item counts,
wall time, memory, CPU, and process count. It sanitizes archive output paths, runs in a
temporary directory inside a non-root container with a read-only artifact mount and
no derived-volume access, and returns only capped `.pyc` children. The webapp checks
child size, magic, and SHA-256, stores bytecode in task-scoped derived storage, then
runs the existing pycdc provider. Database observations retain the executable hash,
archive member path, extractor revision, bytecode hash, and recovered-source hashes.
The container image builds and the webapp type-checks; representative archive runtime,
malformed/high-expansion fixtures, and decompilation fidelity comparison remain open.
Python 2 PYZ and encrypted PYZ archives remain upstream limitations.

## Reuse rules for REAmon

- Prefer calling a mature engine through a narrow adapter over copying its
  parser, decompiler, or disassembler into REAmon.
- Store engine identity, version, input artifact hash, output references, and
  warnings with each run so later AI work can cite the evidence it used.
- Keep the function graph analyzer-neutral: emit stable code-unit entities and
  explicit `calls` relationships into the project store. Scope graph and AI
  neighbor lookups to the same task, provider, and imported artifact; render
  only relationships the analyzer actually resolved. Indirect or unresolved
  targets should remain explicit unknowns instead of guessed edges.
- Treat decompiler output, engine-generated renames, AI drafts, and reviewed
  maintained source as distinct states. Only reviewed maintained source should
  become trusted project-wide naming evidence.
- Scope symbol evidence to the exact imported artifact hash. When a project
  contains multiple versions, show the active binary's evidence first and keep
  older hashes distinct instead of merging same-named units.
- Keep AI rewrites small enough to compare with the original source and bytecode.
  Where a project can be rebuilt, run its actual compiler/checker and preserve
  earlier successful matches when evaluating a new change.
- Before copying source, confirm the exact file's license and retain its notices.
  Prefer subprocess/MCP boundaries when a useful engine has a license that does
  not fit REAmon's distribution model.

## REA MCP workflow audit

REA's current MCP contract returns an `evidence_id`, a normalized result, and a
separate raw provider result when available; successful immutable snapshots are
reused only when binary digest, format, architecture, operation parameters, loader
arguments, and provider identity match. REAmon's database-backed counterpart is
`workspace_list_code_units` plus `workspace_get_code_unit`: it reads the active
workspace's persisted observations and now includes capped native cross-provider
alternates only when the imported input hash, canonical native address identity,
completed task, and saved output hash agree. Source, names, and prototypes remain
attributed to the producing provider. No missing relationship or symbol is filled by
model inference. Reuse REA's evidence identity/cache contract as a design reference;
keep REAmon's project observation and review database authoritative. Add exact xrefs
and CFG context to this surface only when a provider has persisted those facts.

## decomp.wtf source audit

The source was inspected at commit `575b4a30ed481ff5497dfb9ce4f599368a95a04a`,
which is still the `main` tip and the last push reported by GitHub on 2026-10-15.
GitHub currently marks the MIT-licensed repository archived. The final README
describes a loop where agents claim distinct functions, receive assembly, related
data, callers, machine drafts, and previous notes; every attempt is built with
the target compiler and judged; misses return an instruction diff; and accepted
matches are shared and protected from regressions. Its public surface is deliberately
tool-bound: agents use an MCP API without shell access, and parallel helper agents
can work on separate functions. Host-based collaboration rooms coordinate claims
and notes while each member keeps and verifies against their own local game copy.
These are strong workflow and privacy references even though the runtime is tuned
for game projects and reproducible compiler toolchains.

REAmon now has persisted function-level attempts, cross-unit project memory,
conflict-aware merge checks, and scoped MCP reads. The MCP code-unit reader now
pages long provider output by UTF-8 byte offsets while retaining hash verification
and provenance, so agents can read a large function in bounded requests. Remaining
adaptations are a durable multi-client claim queue, provider-specific compiler or
oracle validators with exact input/output receipts, and reviewable cross-unit
symbol changes that protect already-accepted source. Keep REAmon's PostgreSQL
records authoritative; do not transplant the game compiler, ROM adapters, or
SQLite store.

- `src/decompnet/server.py` shows small MCP operations for claiming one function,
  reporting attempts, shared notes, and live status. Map that lifecycle to
  REAmon tasks, evidence, drafts, approvals, and activity rather than transplanting
  its room server.
- `src/decompnet/store.py` persists function claims, attempts, context versions,
  symbols, and events in SQLite. These entities clarify useful project memory,
  but REAmon already has corresponding Prisma/PostgreSQL models and must keep one
  authoritative record set.
- `src/decompnet/similarity.py` ranks MIPS/Thumb code by normalized mnemonic
  frequency, then uses Python's `SequenceMatcher` to compare instruction order.
  REAmon stores bounded operand-free mnemonic signatures for Ghidra, WABT,
  JADX, ILSpy, and Androguard DEX methods, prefilters by length and mnemonic
  frequency, then compares
  matching instruction blocks across completed project runs for the same
  provider. Ghidra matches across artifacts require an exact processor-language
  ID. DEX matches retain their owning class and analysis task; method-level
  Android rewrites map matched method observations back to class records before
  loading reviewed-source and naming context. Syntax-aware method outlines are
  cached against the exact source hash so matching excerpts can be supplied
  without repeating whole class files. Keep the score as a navigation lead,
  never as behavioral validation.
- `compiler.py`, `scoring.py`, and the project adapters judge output with the
  target game's original compiler and byte comparison. That is excellent for
  reproducibly built targets but does not directly validate arbitrary Android
  Java or native artifacts.

## REA Evidence v2 import

REAmon now imports a deliberately bounded subset of canonical [REA Evidence v2 bundles](https://github.com/morluto/rea/blob/9af0b6113c81803f88ec7d242e8fabaaa5d7f1f3/src/domain/evidenceBundle.ts). It verifies strict record shapes, profile and semantic SHA-256 commitments, canonical record ordering, and that all bundle manifests are exactly derived from the records. Uploads are capped at 8 MiB and 1,000 records. Bundles with residual-unknown history are rejected as a whole until REAmon implements its revision and dependency-graph validator. Complete accepted records are retained in the project Evidence table and deduplicated by their semantic evidence ID. Artifact relations are created only for one exact project SHA-256 match; unmatched or ambiguous digests remain unbound. Up to twelve matching imported records are supplied to rewrite context for that exact artifact with provider attribution, limitations, and an explicit untrusted-data caveat. This import preserves evidence for later AI reasoning; it does not treat an external claim as established behavior or recovered source. The interface is a REAmon implementation of the pinned contract, not a runtime dependency on REA's newer-Node package. Residual-unknown import, paged evidence review, and explanation/MCP retrieval remain open.
