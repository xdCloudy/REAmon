# REAmon language and format support matrix

This is the detailed, current-state ledger. The README keeps a shorter WIP summary and
links here. Status describes REAmon integration, not everything an upstream tool can
do. “Planned” means an area to evaluate; it has no delivery date.

## Long-term fluency target

REAmon aims for high practical fluency across all major language families. That means
language-aware unit recovery, readable editable output, consistent project-wide
symbols, and validation appropriate to each toolchain—not merely emitting C-like
pseudocode. The portfolio should include at least native C/C++, Java, Kotlin, C#,
Visual Basic and F#, Python, JavaScript, TypeScript, Go, Rust, Swift, Objective-C,
PHP, Ruby, Lua, WebAssembly toolchains, and assembly across the architectures REAmon
declares supported. Coverage can grow in phases; the matrix must show its actual
state for every family and relevant input format.

“100% fluency” is a product ambition, not a promise of exact original-source
reconstruction. Compilation, optimization, stripping, and obfuscation can erase
comments, local names, formatting, types, or other information, and some behaviors
cannot be distinguished from a static artifact alone. REAmon should make its ambition
measurable along these dimensions:

| Dimension | Evidence required before claiming strong support |
| --- | --- |
| Input coverage | Explicit compiler/runtime versions, bytecode or binary formats, architectures, and known unsupported cases. |
| Unit and symbol recovery | Fixture-backed function/class/module coverage, stable identities, and confidence for names, types, and relationships. |
| Source quality | Language-specific readable output with preserved semantics where evidence permits; generated bridge languages are labeled as such. |
| Safe maintenance | Syntax-aware member edits, project-wide rename consistency, and preserved provenance/diffs. |
| Validation | The strongest available compiler, parser, tests, differential check, or runtime evidence, with limits recorded. |
| Reliability | Versioned clean, optimized, stripped, obfuscated, and malformed fixtures where legally distributable. |

See the [reference portfolio](REAMON_REFERENCE_PORTFOLIO.md) for projects to compare
and the [upstream reuse audit](REAMON_UPSTREAM_REUSE.md) for integration status.

## Source transpilers and native binary lifting: current limits and roadmap

A **source transpiler** translates source code from one programming language to
another. REAmon has a bounded C#-to-Visual-Basic bridge after ILSpy decompilation;
compiled C# and Visual Basic-origin fixtures now pass through ILSpy, translate
to VB, compile, and pass runtime behavior assertions. Obfuscated and project-scale
.NET fixtures remain untested. This is not direct Visual Basic recovery. A
**binary lifter** translates machine instructions into an
intermediate representation (IR), such as LLVM IR or VEX. REAmon also has an
experimental, function-scoped Recurse lift for x86/x64 analysis, but no broad,
architecture-neutral lifting pipeline that emits maintainable source. A decompiler
uses IR and other evidence to emit source-like code. These steps are related, but a
source transpiler does not by itself recover source from a binary, and emitted code
is still a reconstruction.

This work can help RE by making control flow, data flow, calls, and types easier to
compare across architectures and decompiler providers. A stable IR can also give
analysis agents a structured view of operations that is less tied to one assembly
dialect, while a source transpiler can provide maintainers with a language-shaped
bridge when the original language cannot be recovered directly.

Implementation criteria:

- Keep the original binary, raw disassembly, provider output, and every translated
  source or IR artifact separately addressable and hash-linked in the project DB.
- Record the lifter/transpiler name and version, source and target languages, binary
  architecture, ABI, compiler flags when known, and function/address/source mappings.
- Report lift and translation coverage, unsupported instructions, unresolved control
  flow, omitted data, and truncation; missing coverage must remain visible in totals.
- Preserve types, calls, data references, and control-flow edges as evidence with
  provenance and confidence. Do not promote inferred names or semantics silently.
- Validate on versioned, legally redistributable fixtures across architectures,
  compiler versions, optimization levels, stripped/debug binaries, and obfuscation.
  Compare output with known source, compiler results, or differential behavior where
  appropriate; syntax alone is not equivalence.
- Keep each output editable and reviewable, with diffs and human acceptance before it
  becomes maintained source. A bridge language must be labeled as translated output,
  never as recovered original-language source.

**Status: broader evaluation planned.** [rev.ng](https://docs.rev.ng/what-is-revng/) is a
strong reference for QEMU-based multi-architecture lifting into LLVM IR followed by
C decompilation; its project is GPLv2 as a whole. [angr](https://docs.angr.io/en/latest/)
is a BSD-2-Clause reference for architecture-independent binary analysis using IRs
including VEX and P-code. Evaluate provider boundaries, coverage reporting, and
fixture behavior before selecting an engine or copying any code.

## IDA Pro native workflow

An optional IDA Pro provider now runs an operator-supplied, licensed Linux `idat`/`idat64` executable in batch mode. It records Hex-Rays pseudocode, disassembly, function addresses, call edges, and the input artifact hash as project evidence. This is an alternate native C-like representation; it does not recover original C/C++ source. The service must see the installation under `/opt/ida`, and the user must configure the executable in Settings. Windows installations on a browser PC are not available to REAmon's Linux container. See the [IDA Pro integration guide](REAMON_IDA_PRO.md) for setup and current limits. No supported fixture comparison has been completed yet.

## Status definitions

- **Usable:** a supported provider is wired into the workspace for the stated input
  class; users still need to review reconstructed output.
- **Partial / low-level:** useful navigation or an intermediate representation exists,
  but high-level maintainable source is absent or incomplete.
- **Early:** the provider is integrated but its accuracy and supported input range need
  further fixture-based validation.
- **Planned:** no integrated REAmon path currently claims the capability.

## How status should improve

Promote a row only after recording tested input versions, provider version, expected
coverage, failure modes, and applicable validators. Maintain fixtures for clean,
obfuscated, stripped, and malformed samples where licensing and distribution allow.
Do not upgrade a language from “partial” because a generic decompiler emits syntax
that resembles that language.

See [the feature matrix](REAMON_FEATURE_MATRIX.md) for cross-language product status
and [upstream reuse](REAMON_UPSTREAM_REUSE.md) for engine decisions. The Rust DEX
engine is integrated as an early alternate provider; its upstream CFG/xref features
remain evaluation targets and all accuracy claims require fixture-backed validation.
